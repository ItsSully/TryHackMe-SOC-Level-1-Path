# SIEM Triage for SOC

**TryHackMe SOC Level 1 — Module 13**  
**Status:** ✅ Completed

## Overview

This module focused on using Security Information and Event Management (SIEM) platforms to investigate security alerts, analyse logs and identify malicious activity.

I learned how SIEM platforms centralise logs from different sources and allow SOC analysts to search, filter and correlate events to build a clearer picture of an incident.

The module provided practical experience with both **Splunk** and **Elastic/Kibana**, covering Windows, Linux and web-based investigations as well as dedicated alert-triage scenarios.

This room introduced the role of SIEM platforms in SOC investigations and how different log sources can be combined to detect and investigate malicious activity.

### SIEM Benefits

I learned how SIEM platforms provide centralised visibility by collecting logs from multiple sources into one location.

This allows analysts to investigate activity across:

- Endpoints
- Servers
- Network devices
- Web applications
- Security tools

I also learned how **correlation** allows separate events to be linked together to create a more complete picture of an attack.

### Log Sources

The room covered three major categories of log sources:

**Host-based logs**

Logs generated by workstations and servers, including Windows Event Logs and Sysmon.

**Network-based logs**

Logs generated by firewalls, IDS, IPS and other network devices.

**Web-based logs**

Logs generated by web servers and applications, which can reveal scanning, brute-force activity, web shells and DDoS attacks.

### Log Normalisation

I learned why SIEM platforms normalise logs from different systems.

Different sources may use different formats and field names, so normalisation converts them into a consistent structure that makes searching and correlation easier.

# Alert Triage With Splunk

This room focused specifically on investigating security alerts using Splunk.

### Key Areas

- SOC alert triage
- Splunk
- Initial Access
- Brute-force attacks
- Persistence
- Web shells
- Alert investigation
- IOC identification
- Evidence collection
- Incident escalation

### Alert Triage Process

I learned how a SOC analyst can approach an alert systematically rather than immediately assuming that an alert represents a confirmed compromise.

The investigation process involved:

1. Reviewing the alert
2. Identifying the affected host or account
3. Examining the relevant logs
4. Searching for related activity
5. Identifying indicators of compromise
6. Correlating events
7. Determining the nature of the activity
8. Escalating when appropriate

### Initial Access Investigation

I investigated a Linux-based alert involving suspicious authentication activity.

I analysed authentication logs to identify patterns such as:

- Repeated failed logins
- Successful authentication
- Source IP addresses
- Target accounts
- Login timing

This helped determine whether the activity was consistent with a brute-force attack.

### Persistence Investigation

I investigated a Windows alert involving suspicious persistence activity.

I used Windows and Sysmon logs to identify the activity responsible for maintaining access to the compromised system.

This reinforced the importance of correlating process, account and system events rather than analysing one event in isolation.

### Web Shell Investigation

I also investigated an alert involving potential web shell activity.

I analysed web server logs and surrounding events to identify suspicious requests and determine whether the activity could indicate a compromised web server.

### Practical Application

The practical scenarios required me to use Splunk queries to move from an initial alert to supporting evidence.

I learned how to pivot between different log sources and use timestamps, IP addresses, usernames, processes and other indicators to build an investigation timeline.

# Key Takeaways

- SIEM platforms provide centralised visibility across multiple security data sources.
- Log correlation allows analysts to connect individual events and reconstruct attack activity.
- Log normalisation makes data from different systems easier to search and analyse consistently.
- Windows, Linux, network and web logs each provide different pieces of evidence during an investigation.
- Splunk can be used to search large datasets and investigate security alerts efficiently.
- Elastic/Kibana provides similar investigative capabilities through a different SIEM platform.
- Alert triage requires analysts to gather supporting evidence rather than immediately treating an alert as a confirmed incident.
- Process, authentication, network and web activity can be correlated to build an incident timeline.
- Historical events can provide important context when investigating suspicious activity.
- A consistent investigation methodology can be applied across different SIEM platforms.

# Reflection

This module was particularly useful because it brought together many of the skills I had developed throughout the SOC Level 1 pathway.

Instead of investigating individual logs or indicators in isolation, I learned how a SOC analyst can use a SIEM to bring different sources of telemetry together and investigate an alert from multiple angles.

Working with both Splunk and Elastic also helped me understand that although SIEM platforms have different interfaces and query methods, the underlying investigation process remains similar.

The practical scenarios helped me develop a more structured approach to alert triage. I learned to start with the alert, identify the affected asset or account, investigate the surrounding activity, correlate relevant events and use the available evidence to understand what happened.

Overall, this module strengthened my SIEM, log-analysis and alert-triage skills and gave me practical experience investigating Windows, Linux, web and network-based security activity.
