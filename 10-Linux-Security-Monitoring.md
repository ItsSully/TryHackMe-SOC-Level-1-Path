# Linux Security Monitoring

**TryHackMe SOC Level 1 — Module 10**  
**Status:** ✅ Completed

## Overview

This module focused on monitoring and investigating Linux systems using system logs, authentication logs, application logs, Bash history and auditd.

The module covered the different stages of a Linux-based attack, from initial access and discovery through to malware execution, reverse shells, privilege escalation and persistence.

I gained practical experience investigating Linux logs and using process trees and auditd to trace suspicious activity back to its source.

---

# Topics Covered

## Linux Logging for SOC

This room introduced the main Linux log sources used by SOC analysts and how they can be investigated directly from the command line.

### Key Areas

- Linux logging fundamentals
- `/var/log/`
- `/var/log/syslog`
- `/var/log/auth.log`
- Kernel logs
- Application-specific logs
- Package manager logs
- Bash history
- Runtime monitoring
- Auditd
- `ausearch`
- Linux system calls
- Log filtering with `grep`

### Working with Linux Logs

I learned that Linux systems commonly store logs as plain-text files rather than using a central event viewer like Windows.

I practised navigating `/var/log/` and filtering large amounts of log data using command-line tools such as:

- `cat`
- `grep`
- `ls`
- `ausearch`

This helped me understand how SOC analysts can narrow down large volumes of events to find activity relevant to an investigation.

### Authentication Logs

I investigated `/var/log/auth.log` and learned how it can provide information about:

- Successful and failed logins
- SSH sessions
- User sessions
- `sudo` activity
- User management
- Authentication attempts

I also learned how authentication logs can be used to identify suspicious login behaviour and potential brute-force attacks.

### Application and System Logs

I explored additional Linux log sources including:

- `syslog`
- `kern.log`
- Package manager logs
- Web/application logs

This demonstrated how different log sources provide different pieces of information during an investigation.

### Bash History Limitations

I also learned why Bash history should not be treated as a reliable source of evidence.

Attackers can potentially avoid appearing in Bash history by using techniques such as leading spaces, scripts or alternative shells.

This highlighted the importance of using more reliable runtime monitoring such as auditd.

### Auditd

I investigated auditd as a source of runtime telemetry.

I learned how audit rules can monitor important system activity, including:

- Process execution
- File access
- Network activity
- Specific commands

I used `ausearch` to investigate audit events and understand information such as process IDs, parent process IDs, command lines and system calls.

### Practical Application

I worked through Linux log investigations and used multiple log sources to identify suspicious activity.

This helped me understand that effective Linux monitoring often requires correlating information from authentication, application and runtime logs rather than relying on a single source.

# Linux Threat Detection 1

This room focused on detecting **Initial Access** techniques against Linux systems.

### Key Areas

- SSH Initial Access
- SSH authentication
- Password brute-force attacks
- Public-facing services
- Application exploitation
- Process tree analysis
- Supply Chain Compromise
- Auditd investigation

### SSH Attack Detection

I investigated Linux authentication logs to identify suspicious SSH activity.

I looked at:

- Successful SSH logins
- Failed authentication attempts
- Source IP addresses
- Authentication methods
- User accounts
- Login patterns

I used these indicators to identify activity consistent with SSH brute-force attacks and determine when successful access occurred.

### Initial Access via Services

I also investigated how exposed Linux services can provide attackers with an entry point into a system.

Application logs were used to identify suspicious requests and activity, while auditd could then be used to investigate the processes generated by the compromised service.

### Process Tree Analysis

One of the main practical skills developed in this room was **process tree analysis**.

Instead of only looking at a suspicious command, I learned to trace it backwards through its parent processes to determine how it was launched.

For example, a suspicious command could be traced back through a web application or service to identify the original source of execution.

### Supply Chain Compromise

The room also introduced supply chain compromise as another Initial Access technique.

I learned that trusted applications or software dependencies can become a source of compromise if they have been tampered with.

### Skills Applied

- Authentication monitoring
- Source IP investigation
- Application log analysis
- Auditd

### Discovery Activity

I investigated commands used by attackers to gather information about the compromised system.

This included identifying:

- The operating environment
- Running processes
- Security software
- System information
- Users and system activity

I also learned how auditd can help trace discovery commands back to the scripts or processes that launched them.

I investigated how attackers can transfer tools and files onto a compromised Linux system using utilities such as:

- `wget`
- `curl`
- `scp`

I learned that downloaded files need to be investigated in context because legitimate tools and malicious files can both be transferred using the same utilities.

The investigation involved analysing:

- Authentication logs
- Auditd events
- Process execution
- File transfers
- Malware paths
- Network activity

I also investigated how the malware attempted to identify security software and scan other systems for exposed SSH services.

### Practical Application

The practical investigation helped me understand how multiple pieces of Linux telemetry can be combined to reconstruct an attack.

Rather than analysing a single suspicious event, I followed the sequence of attacker actions and used logs to understand how the compromise progressed.

### Reverse Shell Detection

I investigated how attackers can use command injection to execute commands on a Linux host and establish a reverse shell.

I used auditd logs to trace suspicious commands back through their parent processes and identify how the reverse shell activity originated.

### Privilege Escalation

I investigated activity associated with attackers attempting to gain higher privileges.

This included looking for commands used to:

- Search for credentials
- Access sensitive configuration files
- Switch users
- Escalate privileges to root

I learned how auditd process information can help reconstruct the commands used during privilege escalation.

### Persistence

The room introduced several Linux persistence techniques.

I investigated persistence through:

- Malicious services
- Cron jobs
- Newly created accounts
- SSH authorized keys

These techniques demonstrated how attackers can maintain access even after their initial session has ended.

### Practical Investigation

I used Linux audit logs and authentication logs to investigate suspicious activity across multiple stages of an attack.

This involved tracing processes, examining command lines, investigating modified files and identifying persistence mechanisms.

# Key Takeaways

- Linux systems generate valuable security telemetry across multiple log sources.
- `/var/log/auth.log` is particularly useful for investigating authentication and SSH activity.
- Auditd provides visibility into runtime events such as process execution and file activity.
- Bash history should not be treated as a complete or reliable record of attacker activity.
- Process tree analysis can help identify where suspicious commands originated.
- Attackers can use legitimate Linux utilities such as `wget`, `curl` and `scp` to transfer tools or malware.
- Linux attacks can progress from Initial Access to discovery, malware deployment, privilege escalation and persistence.
- Effective investigations require correlating multiple sources of evidence rather than relying on a single log.
